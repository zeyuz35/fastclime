## 2024-05-18 - Prevent Zero-Length Memory Allocation Errors
**Vulnerability:** The C memory management macros (`MALLOC`, `CALLOC`, `REALLOC`) passed the `len` parameter directly to `malloc()`, `calloc()`, and `realloc()`. If `len` evaluated to `0`, standard C behavior allows these functions to return `NULL`. This would trigger the macro's error handling condition (`if ((name) == NULL)`), mistakenly causing a fatal R `error()` due to "Memory allocation failed" rather than processing an empty array. Additionally, evaluating the `len` argument multiple times in macro expansion could cause double-evaluation hazards if expressions with side-effects were passed.
**Learning:** Returning `NULL` on a zero-length allocation request can create confusing and application-crashing behaviors (fatal `error()`) instead of safely continuing execution. Standardizing safe lengths and single evaluation using local variables in macros avoids both double-evaluation and erroneous `NULL` error triggers.
**Prevention:** Ensure C macros evaluate arguments strictly once by assigning them to a local typed variable (e.g., `size_t _safe_len = (size_t)(len)`). **Vulnerability:** Core functions `fastclime()` and `dantzig()` calculate allocation sizes for matrices that are passed to `.C()`. When evaluating dimensions like `d0 * d0 * nlambda` using R's default 32-bit signed integers, inputs with `d0 >= 46342` cause a silent integer overflow before allocation, leading to uncatchable fatal crashes and memory corruption.
**Learning:** Multiplying dimensions natively in R can overflow `.Machine$integer.max` without warning if variables are implicitly typed as `integer` (via `as.integer()` or default generation).
**Prevention:** Explicitly cast dimensional variables to `numeric` using `as.numeric()` before multiplication to calculate the true double-precision required size, and explicitly validate it against `.Machine$integer.max` to securely trap requests that exceed C layer limits before invoking C code.
